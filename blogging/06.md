# [InfraPilot] Lambda + RDS + EC2 하이브리드 아키텍처 설계 — 왜 서버리스와 서버를 같이 쓰는가

## 카테고리: Infra / Cloud Architecture

---

## 배경

AI 에이전트 5명이 15분마다 100개 코인을 분석하고, 사용자는 웹 대시보드에서 결과를 봅니다. 이걸 **어떤 구조로 돌릴 것인가?**

### 선택지

```
A. EC2 하나에 다 올리기
B. 전부 Lambda (서버리스)
C. Lambda + EC2 하이브리드
```

C를 선택했습니다.

---

## 왜 EC2만으로 안 되는가

```
EC2 t3.micro (1GB RAM)에서:
- 웹 서버 (FastAPI)
- 15분마다 AI 분석 (100 코인 × 5 Agent)
- DB 조회/저장
→ 메모리 부족, 분석 중 웹 응답 느려짐
```

**배치 작업과 웹 서버가 같은 서버에 있으면 서로 방해합니다.**

## 왜 전부 Lambda로 안 되는가

```
Lambda 제약:
- 최대 실행 시간 15분
- WebSocket 지원 안 됨
- 콜드 스타트 지연 (1~5초)
→ 실시간 대시보드에 부적합
```

**Lambda는 "실행하고 끝"이라 상시 연결이 필요한 웹 서버에 적합하지 않습니다.**

---

## 하이브리드 설계

각 서비스의 **강점에 맞게** 역할을 분리했습니다.

```
┌─ EventBridge (15분 주기) ─────────────────┐
│ cron(0/15 * * * ? *)                      │
└────────────┬───────────────────────────────┘
             │ 트리거
             ▼
┌─ Lambda (배치 분석) ──────────────────────┐
│ 1. Bybit API → OHLCV 수집                │
│ 2. AI Agent 팀 실행 (분석)                │
│ 3. 결과 → RDS 저장                        │
└────────────┬───────────────────────────────┘
             │ SQL
             ▼
┌─ RDS PostgreSQL (데이터 저장) ────────────┐
│ analyses, coins, sectors 테이블           │
└────────────┬───────────────────────────────┘
             │ SELECT
             ▼
┌─ EC2 (웹 대시보드) ──────────────────────┐
│ FastAPI → RDS 조회 → 사용자에게 표시      │
└───────────────────────────────────────────┘
```

### 역할 분리

|서비스|역할|왜 이 서비스인가|
|---|---|---|
|EventBridge|15분 스케줄|AWS 네이티브 cron, 무료|
|Lambda|AI 분석 배치|실행 시에만 과금, 자동 스케일|
|RDS|데이터 저장|Lambda + EC2 둘 다 접근 가능|
|EC2|웹 서버|상시 실행, WebSocket 가능|

## 비용 분석

```
Lambda:
  15분 × 4회/시간 × 24시간 × 30일 = 2,880회/월
  무료 한도: 100만 회/월
  → ₩0

RDS:
  db.t4g.micro, 20GB
  Free Tier 12개월
  → ₩0

EC2:
  t3.micro
  Free Tier 12개월
  → ₩0

EventBridge:
  무료

총: ₩0 (Free Tier 기간 내)
```

Free Tier 만료 후에도 Lambda는 거의 무료, EC2 + RDS만 과금. 비용 효율적인 구조입니다.

---

## 장애 격리

이 구조의 숨은 장점:

```
Lambda 실패 시:
  → 웹은 정상 (기존 분석 결과 표시)
  → "마지막 분석: 15분 전" 표시만 됨

EC2 다운 시:
  → Lambda는 계속 돌아감 (데이터 쌓임)
  → EC2 복구하면 즉시 최신 데이터 표시

RDS 장애 시:
  → 둘 다 영향. 하지만 RDS는 자동 백업 + 복구
```

각 컴포넌트가 독립적이라 **하나가 죽어도 전체가 멈추지 않습니다.**

---

## RDS를 SQLite 대신 선택한 이유

|항목|SQLite|RDS|
|---|---|---|
|Lambda 접근|불가 (Lambda는 stateless)|가능 (네트워크 접근)|
|동시 쓰기|락 문제|안전|
|백업|수동|자동|
|포트폴리오|흔함|차별화|

Lambda는 실행될 때마다 새로운 환경에서 시작하기 때문에 **파일 기반 DB(SQLite)를 쓸 수 없습니다.** RDS처럼 네트워크로 접근하는 DB가 필수입니다.

## Lambda 실행 흐름 (상세)

```python
def lambda_handler(event, context):
    # 1. 분석 대상 코인 목록 (RDS에서)
    coins = db.query("SELECT symbol FROM coins WHERE enabled = true")
    
    # 2. 코인별 분석
    for coin in coins:
        # a. 시장 데이터 수집
        ohlcv = fetch_ohlcv(coin.symbol, timeframe="15m", limit=50)
        
        # b. Analyst → 기술 분석
        analysis = await analyst.process(ohlcv)
        
        # c. Strategist → Neely 기반 시그널
        signal = await strategist.process(ohlcv, analysis)
        
        # d. Risk Manager → 검증
        risk = await risk_manager.process(signal)
        
        # e. RDS에 저장
        db.insert("analyses", symbol=coin.symbol, signal=signal, risk=risk)
    
    # 3. 섹터별 집계
    aggregator.aggregate_sectors()
    
    return {"statusCode": 200, "analyzed": len(coins)}
```

코인 20개 기준, AI 호출 약 40회, 실행 시간 약 2분. Lambda 15분 제한 내 충분합니다.

## EC2 웹 서버 (가벼움)

```python
@app.get("/")
async def dashboard():
    coins = db.query("""
        SELECT c.symbol, c.sector, a.signal, a.confidence, a.wave_position
        FROM coins c
        JOIN analyses a ON c.symbol = a.symbol
        WHERE a.analyzed_at = (SELECT MAX(analyzed_at) FROM analyses WHERE symbol = c.symbol)
        ORDER BY a.confidence DESC
    """)
    
    sectors = db.query("SELECT * FROM sector_summaries")
    return render("dashboard.html", coins=coins, sectors=sectors)
```

**DB 조회만** 하기 때문에 t3.micro로 충분합니다. AI 분석은 Lambda가 하니까 EC2에 부하가 없습니다.

## Terraform 추가 사항

기존 VPC/EC2에 RDS + Lambda를 추가합니다:

```
modules/
├── vpc/       (기존)
├── security/  (기존 + RDS용 SG 추가)
├── compute/   (기존)
├── database/  (신규: RDS)
└── lambda/    (신규: Lambda + EventBridge)
```

RDS는 보안상 **Private Subnet**에 배치해야 합니다. EC2와 Lambda만 접근 가능하도록 Security Group으로 제한합니다.

## 정리

|설계 결정|이유|
|---|---|
|하이브리드 (Lambda + EC2)|배치와 웹의 특성이 다름|
|Lambda for 분석|실행 시에만 과금, 자동 스케일|
|EC2 for 웹|상시 실행 필요, WebSocket|
|RDS for 저장|Lambda/EC2 공유, 동시 접근 안전|
|EventBridge for 스케줄|AWS 네이티브, 무료, 안정적|
|Private Subnet for RDS|DB 직접 노출 방지, 보안 기본|
