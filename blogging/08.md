# [InfraPilot] Terraform으로 RDS 모듈화하기 — Root Wiring, Security Group 체인, validate 오류까지 한 번에 정리

## 카테고리: Infra / Terraform / AWS

---

## 왜 RDS를 모듈로 분리했나

InfraPilot은 EC2(애플리케이션)와 RDS(PostgreSQL)를 분리해 운영합니다.  
핵심은 다음 두 가지입니다.

1. DB를 Private 영역에 두고 접근 경로를 최소화한다.
2. Terraform 모듈 경계(입력/출력)를 명확하게 유지한다.

이번 글은 **Python 로직 없이**, 실제 Terraform 코드 기준으로 RDS 모듈 구성과 wiring, 그리고 `terraform validate`에서 만난 오류를 어떻게 정리했는지까지 다룹니다.

---

## 최종 구조 (현재 코드 기준)

루트 모듈에서 `vpc`, `security`, `rds_security`, `rds`, `compute`를 조합합니다.

```hcl
module "rds_security" {
  source    = "./modules/rds_security"
  vpc_id    = module.vpc.vpc_id
  ec2_sg_id = module.security.sg_id
}

module "rds" {
  source             = "./modules/rds"
  db_username        = var.db_username
  db_password        = var.db_password
  private_subnet_ids = [module.vpc.private_subnet1_id, module.vpc.private_subnet2_id]
  rds_sg_id          = module.rds_security.sg_id
}
```

흐름은 단순합니다.

- `security` 모듈이 EC2 SG 생성
- `rds_security` 모듈이 RDS 전용 SG 생성 + EC2 SG만 인바운드 허용
- `rds` 모듈이 private subnet group + PostgreSQL 인스턴스 생성

## 디렉터리 설계

```text
iac/
├── main.tf
├── variables.tf
├── output.tf
└── modules/
    ├── rds/
    │   ├── main.tf
    │   ├── variables.tf
    │   └── outputs.tf
    └── rds_security/
        ├── main.tf
        ├── variables.tf
        └── outputs.tf
```

이렇게 분리하면 다음 장점이 있습니다.

- DB 엔진/스펙 변경은 `modules/rds` 안에서만 처리 가능
- 보안 정책 변경은 `modules/rds_security`에서만 처리 가능
- 루트 모듈은 "조립자(orchestrator)" 역할에 집중

## 1) rds_security 모듈: 접근 제어 전담

### 입력 변수

```hcl
variable "vpc_id" {
  type = string
}

variable "ec2_sg_id" {
  type = string
}
```

### 리소스

```hcl
resource "aws_security_group" "pilot_rds_sg" {
  name        = "pilot_rds_sg"
  description = "infrapilot rds sg"
  vpc_id      = var.vpc_id
}

resource "aws_vpc_security_group_ingress_rule" "allow_ec2_to_postgres" {
  security_group_id            = aws_security_group.pilot_rds_sg.id
  referenced_security_group_id = var.ec2_sg_id
  from_port                    = 5432
  ip_protocol                  = "tcp"
  to_port                      = 5432
}

resource "aws_vpc_security_group_egress_rule" "rds_outbound" {
  security_group_id = aws_security_group.pilot_rds_sg.id
  cidr_ipv4         = "0.0.0.0/0"
  ip_protocol       = "-1"
}
```

여기서 중요한 포인트:

- 인바운드를 **CIDR이 아니라 SG 참조**(`referenced_security_group_id`)로 제한
- 즉, 특정 IP 대역이 아니라 "EC2 SG를 가진 인스턴스"만 DB 접근 가능
- 이후 Lambda를 붙일 때도 같은 패턴으로 `lambda_sg_id`를 추가하면 됨

### 출력

```hcl
output "sg_id" {
  value = aws_security_group.pilot_rds_sg.id
}
```

## 2) rds 모듈: DB 인스턴스 전담

### 입력 변수

```hcl
variable "private_subnet_ids" {
  type = list(string)
}

variable "db_username" {
  type = string
}

variable "db_password" {
  type      = string
  sensitive = true
}

variable "rds_sg_id" {
  type = string
}
```

### 리소스

```hcl
resource "aws_db_subnet_group" "main" {
  name       = "infrapilot-db-subnet-group"
  subnet_ids = var.private_subnet_ids
}

resource "aws_db_instance" "main" {
  identifier        = "infrapilot-db"
  engine            = "postgres"
  engine_version    = "15"
  instance_class    = "db.t3.micro"
  allocated_storage = 20

  db_name  = "infrapilot"
  username = var.db_username
  password = var.db_password

  db_subnet_group_name   = aws_db_subnet_group.main.name
  vpc_security_group_ids = [var.rds_sg_id]

  publicly_accessible = false
  skip_final_snapshot = true
}
```

설계 의도:

- `publicly_accessible = false`로 외부 직접 노출 차단
- `db_subnet_group`에 private subnet 2개를 넣어 AZ 분산 기반 확보
- 보안그룹은 루트에서 주입 (`var.rds_sg_id`)받아 모듈 결합도 감소

### 출력

```hcl
output "db_endpoint" {
  value = aws_db_instance.main.endpoint
}

output "db_name" {
  value = aws_db_instance.main.db_name
}
```

## 3) 루트 변수/출력 연결

RDS 입력을 루트에서 받도록 선언합니다.

```hcl
variable "db_username" {
  type = string
}

variable "db_password" {
  type      = string
  sensitive = true
}
```

그리고 루트 출력에서 모듈 출력을 다시 노출합니다.

```hcl
output "db_endpoint" {
  value = module.rds.db_endpoint
}

output "db_name" {
  value = module.rds.db_name
}
```

이 구조 덕분에 상위 스택/운영자가 `module.rds.*` 내부를 몰라도 루트 output만으로 필요한 정보에 접근할 수 있습니다.

## validate에서 실제로 부딪힌 오류와 원인

### 1) `No module call named "lambda"`

원인:

- 루트에서 `module.lambda.lambda_sg_id`를 참조했지만 lambda 모듈이 아직 없음

정리:

- 당장 사용하지 않는 `lambda_sg_id` wiring 제거
- 추후 lambda 모듈 추가 시 `rds_security`에 입력 변수로 다시 확장

### 2) `tfvar.db_username` / `tfvar.db_password` undeclared resource

원인:

- `tfvar`는 Terraform 문법이 아님 (`var.*`가 맞음)

정리:

- `db_username = var.db_username`
- `db_password = var.db_password`

### 3) `module.rds_security.rds_sg_id` unsupported attribute

원인:

- `rds_security` 모듈 output 이름은 `sg_id`인데 루트에서 `rds_sg_id`로 참조

정리:

- `rds_sg_id = module.rds_security.sg_id`로 수정

### 4) `aws_security_group.ec2_sg` undeclared resource (모듈 내부)

원인:

- `modules/rds_security/main.tf`에서 내부에 없는 리소스 이름을 직접 참조

정리:

- 리소스 직접참조 대신 입력 변수 `var.ec2_sg_id` 사용

## Terraform 모듈 인터페이스 관점에서 배운 점

핵심 규칙 하나로 대부분의 오류를 줄일 수 있습니다.

> **모듈 내부에서는 외부 리소스 이름을 직접 참조하지 말고, 반드시 변수로 주입받아라.**

즉:

- 나쁜 패턴: `aws_security_group.ec2_sg.id` (모듈 외부 리소스 가정)
- 좋은 패턴: `var.ec2_sg_id` (계약 기반 입력)

이 규칙을 지키면 모듈 재사용성, 테스트 용이성, refactor 안정성이 동시에 올라갑니다.

## 실행 예시 (민감정보는 tfvars로)

```bash
cd iac
terraform init
terraform validate
terraform plan \
  -var="db_username=YOUR_DB_USER" \
  -var="db_password=YOUR_DB_PASSWORD"
```

운영에서는 `-var` 대신 `*.tfvars` 또는 환경변수 사용을 권장합니다.

## 다음 확장 포인트 (Lambda 추가 예정 기준)

Lambda를 붙일 때는 아래 순서로 확장하면 됩니다.

1. `modules/lambda` 생성 후 `lambda_sg_id` output 노출
2. `modules/rds_security/variables.tf`에 `lambda_sg_id` 추가
3. `allow_lambda_to_postgres` ingress rule 추가
4. 루트 `main.tf`에서 `lambda_sg_id = module.lambda.lambda_sg_id` 연결

중요한 건, **lambda를 아직 만들지 않았을 때는 참조를 절대 먼저 넣지 않는 것**입니다.

## 마무리

이번 RDS 모듈 작업의 핵심은 "RDS 생성" 자체보다, **모듈 간 인터페이스를 정확히 맞추는 것**이었습니다.

- `rds_security`는 SG 정책만 책임진다.
- `rds`는 DB 인스턴스만 책임진다.
- 루트는 변수/출력 wiring만 책임진다.

이 역할 분리만 지켜도 `terraform validate` 단계에서 대부분의 참조 오류를 조기에 차단할 수 있습니다.
